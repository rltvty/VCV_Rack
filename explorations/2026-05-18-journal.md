## 20:46 CEST - Hot reconnect bug traced to stale port state

- Root cause:
  Rack's RtAudio layer calls `onStopStream()` when the hardware stream is disconnected, but `audio::Port` does not automatically clear its `device` pointer or `deviceId`

  added explicit `streamActive` tracking
  treat a device as connected only when both the device pointer exists and the stream is active
  on live stream stop, schedule immediate reconnect and mark the port inactive
  before reconnecting, clear stale device state with `setDeviceId(-1)` so resubscribe is not blocked by the old `deviceId`
  updated the display and widget polling logic to use the live-connection state instead of raw `getDevice()`

## 20:59 CEST - Sample-rate forcing behavior

- Investigated whether Rack or the split plugin can force a hardware sample rate for devices such as `Mask1EX MK2 USB Audio`, which is currently opening at `38000` in the Rack log.
- Relevant code paths:
  `src/rtaudio.cpp`
  `src/audio.cpp`
  `src/app/AudioDisplay.cpp`
  `standalone/RltvtyAudioIO/src/AudioSplit.cpp`
- Key findings:
  Rack does expose a per-device sample-rate chooser through `AudioSampleRateChoice`
  selecting a sample rate calls `audio::Port::setSampleRate()`, which closes and reopens the underlying audio device
  Rack does not force an arbitrary sample rate; in `src/rtaudio.cpp` it chooses the closest value from `deviceInfo.sampleRates`
  after opening the stream, Rack updates to the actual stream sample rate returned by `rtAudio->getStreamSampleRate()`
  this means Rack can request 48 kHz only if the device/driver reports 48 kHz as a supported rate
- Important distinction:
  hardware device sample rate and Rack engine sample rate are separate
  the engine sample rate can be fixed globally, but the hardware stream still opens at whatever Core Audio / RtAudio negotiates for that device
  Rack then sample-rate-converts between the device and the engine if needed
- Current evidence:
  Rack log shows:
  `Opening RtAudio Core Audio device 129: Mask1EX MK2 USB Audio (2 in, 0 out, 38000 sample rate, 256 block size)`
  so the current hardware negotiation path believes the device is at `38 kHz`
