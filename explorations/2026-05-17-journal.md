## 21:49 CEST - Initial plugin development exploration

- Current goal: assess whether this Rack fork is a useful reference base for building our own plugins and identify the lowest-friction path for a non-C++ workflow.
- Files explored: `README.md`, `plugin.mk`, `helper.py`, `Core.json`, `include/rack.hpp`, `include/helpers.hpp`, `include/engine/Module.hpp`, `include/app/ModuleWidget.hpp`, `include/componentlibrary.hpp`, `src/core/plugin.cpp`, `src/core/Notes.cpp`, `src/core/CV_MIDI.cpp`, `src/core/MIDI_Gate.cpp`.
- Important repo shape finding: this is the Rack application source plus the public plugin API plus bundled Core modules. There is no checked-in third-party example plugin under `plugins/`, so the best local learning examples are the built-in modules in `src/core/`.
- Important API finding: plugin code should treat `include/rack.hpp` as the supported public API surface. The repo explicitly warns against depending on internal headers directly from plugin code.
- Module architecture finding: the core split is clean and reusable.
  `engine::Module` holds DSP/state and port/param/light definitions.
  `app::ModuleWidget` holds panel layout and UI behavior.
  `createModel<TModule, TWidget>()` wires those together.
  `init(Plugin* p)` registers models.
  `plugin.json`/manifest metadata controls browser-facing plugin and module metadata.
- Learning-path finding: `src/core/Notes.cpp` is the best beginner example because it has almost no DSP and clearly shows state persistence plus UI wiring. `src/core/CV_MIDI.cpp` is a good second example because it shows a real `process()` loop, serialization, stock UI components, and a context menu.
- Build/scaffold finding: `plugin.mk` contains the standard plugin build/package/install flow, and `helper.py` can scaffold a plugin plus generate module boilerplate from an SVG panel. This is likely the fastest practical way to start a custom module here.
- UI/component finding: `include/componentlibrary.hpp` exposes a large stock set of reusable widgets like `ThemedPJ301MPort`, `RoundLargeBlackKnob`, `CKSS`, screws, and lights. This means a first plugin can lean heavily on built-in Rack visuals and avoid custom widget work.
- Constraint noted: for our own plugin work, starting with utility or MIDI/CV helper modules is much more realistic than starting with a DSP-heavy oscillator or filter.
- Promising first-module directions: trigger/gate helper, attenuverter/offset utility, simple CV router/splitter, or a MIDI helper derived from Core module patterns.
- Open questions:
  how much of this fork differs materially from upstream Rack for plugin-facing behavior
  whether we want plugin experiments to live inside this repo as local references or in a separate plugin repo that points at this Rack tree via `RACK_DIR`
- Likely next steps:
  do a line-by-line walkthrough of one minimal module
  scaffold a tiny plugin with `helper.py`
  implement a deliberately simple first module that copies proven patterns from `src/core/`

## 22:10 CEST - Split audio module prototype

- Current goal: test whether the built-in Core audio interface can be split into separate hardware-input and hardware-output modules without changing Rack host internals.
- Files explored further: `src/core/Audio.cpp`, `src/audio.cpp`, `src/rtaudio.cpp`, `src/app/AudioDisplay.cpp`, `include/audio.hpp`, `include/app/AudioDisplay.hpp`.
- Important finding: split modules are feasible with the existing `audio::Port` abstraction. A single hardware device can already be shared across multiple subscribed ports, and each port can independently use `inputOffset`, `outputOffset`, `maxInputs`, and `maxOutputs`.
- Important finding: the current restore path is not sufficient for sticky reconnect behavior.
  `audio::Port::toJson()` stores the active device name, but only if a device is currently connected.
  `audio::Port::fromJson()` restores by device name, but `setDriverId()` auto-binds the driver's default device first.
  This means a missing target device can silently fall back to a default device, and a later save while disconnected can lose the prior selection entirely.
- Prototype implementation added under `plugins/RltvtyAudioIO/`.
  Files added:
  `plugins/RltvtyAudioIO/plugin.json`
  `plugins/RltvtyAudioIO/Makefile`
  `plugins/RltvtyAudioIO/src/plugin.hpp`
  `plugins/RltvtyAudioIO/src/plugin.cpp`
  `plugins/RltvtyAudioIO/src/AudioSplit.cpp`
- Prototype scope:
  six models: `AudioIn2`, `AudioIn8`, `AudioIn16`, `AudioOut2`, `AudioOut8`, `AudioOut16`
  uses the existing Rack audio engine model rather than modifying host code
  adds a custom sticky device state with:
  desired device name
  desired sample rate
  desired block size
  auto-reconnect flag
- Reconnect behavior in the prototype:
  on patch load, restore the driver, immediately clear the driver's default device binding, then try to reconnect only to the saved device name
  if the device is missing, keep the saved target instead of clearing it
  widget `step()` polls once per second on the UI thread and reconnects if the named device reappears
- Important limitation: the prototype currently keys the lock by device name, not by a stronger persistent hardware identifier. If two devices expose the same name, the first match wins.
- Important limitation: hot unplug/replug while Rack is already running is only partially addressed. The prototype can reconnect a missing-at-load device when it later appears, but it does not yet add robust unplug detection or error recovery for an already active stream.
- Important limitation: the plugin uses a simple programmatic panel instead of final SVG artwork. This is intentional for the first pass so the behavior can be explored without spending time on panel assets.
- Build verification blocker:
  local plugin build failed before compiling the plugin logic because this checkout does not currently have `dep/include`
  `make dep` also failed because it tries to fetch third-party archives and the environment lacks `wget`
  so the code was API-sanity-checked locally, but not fully compiled in this environment
- Likely next steps:
  prepare the Rack dependency tree and run a real plugin build
  decide whether lock persistence should stay plugin-local or be generalized in Rack's `audio::Port`
  improve the UI around "locked device" state, especially to distinguish "temporarily missing" from "user intentionally chose no device"
